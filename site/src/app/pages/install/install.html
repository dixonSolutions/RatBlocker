Install

Nothing here goes through an app store. Build it yourself, or take the release artifacts and install them locally.

RatBlocker is at v0.1.0 and has not been through a security audit. It filters correctly and is covered by tests, but treat it as early software.

Build it first

Every install path starts from a build. You need Rust 1.82 or newer and Node 20.11 or newer. 

git clone {{ project.repository }}.git
cd RatBlocker
cargo build --release

# Compile the bundled filter lists into dist/
./target/release/ratblocker-compile build \
    --list easylist=filter-lists/bundled/easylist.txt \
    --list easyprivacy=filter-lists/bundled/easyprivacy.txt \
    --out dist

# Build the engine for the browser, then both extensions
rustup target add wasm32-unknown-unknown
cargo build --release -p ratblocker-wasm --target wasm32-unknown-unknown
cd extensions && npm install && node build.mjs

Pick a platform

Chromium & Chrome Firefox & forks

Chromium, without the Web Store

Chromium on Linux can install an extension from a local CRX through its external extension mechanism. No store, no developer-mode flag, and it survives restarts. 

cd extensions && node package.mjs chromium

sudo install -Dm644 dist/ratblocker-chromium.crx \
    /usr/share/ratblocker/ratblocker-chromium.crx
sudo install -Dm644 dist/{{ project.chromiumExtensionId }}.json \
    /usr/share/chromium/extensions/

The extension id is derived from the signing key that package.mjs generates on first run.

Keep chromium-signing-key.pem and back it up. The extension id comes from it, so losing it changes the id and orphans every existing install. It is gitignored — do not commit it.

Hosting it remotely

To update installs from a server rather than by hand, publish the CRX alongside chromium-update.xml and deploy the generated policy: 

sudo install -Dm644 dist/chromium-policy.json \
    /etc/chromium/policies/managed/ratblocker.json

Set RATBLOCKER_UPDATE_BASE when packaging so the manifest points at your host rather than the placeholder.

The signing situation, honestly

Release Firefox will not permanently install an unsigned extension. There is no preference, no enterprise policy and no local file that changes this — Mozilla removed those routes years ago, and self-signing is not a thing Firefox recognises.

So there are two honest options.

Option 1 — a Gecko fork that does not enforce signing

Forks built without MOZ_REQUIRE_SIGNING take the unsigned XPI directly and keep it across restarts. Zen, LibreWolf, Waterfox and Mullvad Browser all qualify, as do Mozilla's own Developer Edition, Nightly, ESR and unbranded builds. 

cd extensions && node package.mjs firefox

Set xpinstall.signatures.required to false in about:config, then about:addons → gear → Install Add-on From File and pick dist/ratblocker-firefox-0.1.0.xpi.

Not sure whether a given build enforces signing? Ask it:

node tests/browser/gecko-signing.mjs /path/to/browser dist/ratblocker-firefox-0.1.0.xpi

It attempts a permanent unsigned install and tells you which category the build falls into. A temporary install would prove nothing, since that bypasses the check anyway.

Option 2 — unlisted signing on AMO

Mozilla will sign an extension without publishing it. Unlisted signing has no review queue and nothing appears in the public directory; you host the file and its updates yourself. It needs an AMO API key. 

export AMO_JWT_ISSUER=user:12345:67
export AMO_JWT_SECRET=...
node extensions/sign-firefox.mjs

Produces a signed XPI plus firefox-updates.json, the manifest Firefox polls for self-hosted updates. A signed XPI installs everywhere, forks included, so signing once covers every Gecko browser.

Using it in a Flatpak browser

A sandboxed browser can only read files it has been granted. Put the XPI somewhere it can reach — ~/Downloads is granted by default in most browser Flatpaks — or open up access with Flatseal.
