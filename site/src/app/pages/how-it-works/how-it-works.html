How it works

One engine, three ways of reaching it. Everything below describes what the code actually does, including where it gives up.

One engine, compiled twice

The filtering logic is a single Rust crate. It is compiled to WebAssembly for the browser extensions, which is what stops the two drifting apart: a rule that blocks in Firefox blocks identically on the system layer, because it is literally the same code reaching the same conclusion.

Filter lists are not parsed at startup. A compiler turns them into a versioned binary database ahead of time, and the runtime loads that. It is why a fresh install starts blocking on the first request without contacting anything.

Fitting EasyList into Manifest V3

Chromium caps an extension at {{ facts.chromium.maxStaticRules.toLocaleString() }} static rules. The compiled lists produce {{ facts.chromium.candidates.toLocaleString() }} candidates, so a naive conversion has to throw most of them away — which is why several MV3 blockers cover far less than their Manifest V2 versions did.

RatBlocker avoids that. The overwhelming majority of EasyList rules are plain domain blocks, and Chromium's requestDomains condition already matches a domain and all its subdomains. Collapsing them turns {{ facts.chromium.collapsedDomains.toLocaleString() }} separate rules into {{ facts.chromium.collapsedIntoRules }}.

Untrusted input, treated as such

A filter list is a file from the internet, so the parser is written as though every list is hostile. Patterns too generic to index are refused. Regular expressions are size-capped and run on a linear-time engine, so a crafted pattern cannot hang the browser. $redirect targets must name a resource RatBlocker ships — an early version accepted a full URL, which would have let a list quietly redirect your traffic anywhere.

Rules that cannot be honoured are rejected and counted, never ignored in silence. The current lists yield {{ facts.rejected }} rejections, and every build writes them out with a reason attached.
